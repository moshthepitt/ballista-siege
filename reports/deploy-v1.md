# Deploy pass DP1

Ballista Siege now starts a casual offline run immediately. Devnet support loads when Fund opens, or after the board becomes interactive if a burner is saved. A new run uses devnet only when its deployment, program, templates and balance checks pass. Opening Fund does not replace an offline run already in progress. Compact header badges and retry labels abbreviate long seeds; the chooser, URL and accessible label retain the full value.

Removed Daily selection, its button, copy and HUD label. No seed parameter now chooses a random seed; `?seed=N` remains reproducible. All runs use the existing `practice` state bit. Per-seed best scores, retry, New seed, plan comparison and unranked replan remain.

## Browser and deployment split

`src/chain-v1/wire.ts` encodes the existing run instructions, derives template and registry addresses, validates template headers, and decodes registry state and attributed run events. `run-layout.ts` is generated by `pnpm generate:wire` from the SDK compiler's state input order, account roles and registry indices. Browser code imports neither Ballista SDK entry point. Vite compiles on the build host to reject stale layouts and manifest payload hashes before publishing. Deploy scripts and the reference client still use the SDK compiler.

The parity suite compares creators, ID sets, players, seeds, modes, action queues, every step cursor, transaction resume boundaries, template headers, registry snapshots and nested event logs. VM recovery tests exercise the browser wire path, persisted journals, signature timeouts, pre-signing failures and a known program mismatch. A failure before a signature restores the journal index so retry cannot mistake it for another tab. No rules source or existing chain source changed. Template payloads, IDs, instruction bytes and addresses retain their previous derivation.

Vite imports the selected deployment into the lazy chain chunk. Production selects `play/deployments/devnet.json`; development prefers `localnet.json` when available. There is no deployment JSON fetch or JSON artifact in `dist`. Builds with and without a devnet manifest pass. Assets use relative URLs and work under a Pages subpath.

## Funding

Open Offline or the devnet badge, then Fund. The panel shows the burner address, balance, a conservative run estimate, refresh and the stated rent and transaction costs. Request airdrop submits one 0.1 SOL request. Refusal says "Faucet busy" and offers the Solana faucet or a wallet transfer. The faucet link copies the address before opening its new tab.

Send from wallet discovers devnet wallets through [Wallet Standard registration events](https://github.com/wallet-standard/wallet-standard/blob/master/packages/core/wallet/src/register.ts). It connects an account supporting `solana:signAndSendTransaction` and asks it to send a hand-encoded 0.02 SOL System transfer. The [standard transaction feature](https://github.com/wallet-standard/wallet-standard/blob/master/packages/example/wallets/src/solanaWallet.ts) receives serialized transaction bytes. Game turns continue to use the burner.

Copy or download exports a Solana CLI 64-byte JSON keypair. Restore checks its public bytes against the secret before replacing browser storage. The panel says the key is devnet-only and its holder controls the burner. Storage failures remain contained; a tab can still export its in-memory key.

RPC Save and Reset validate the URL and genesis hash before storing it. HTTPS is accepted; HTTP is limited to localhost addresses. Production rejects every genesis hash except devnet. An active transaction prevents changing RPC; an idle failed turn can move to a checked devnet endpoint while retaining its signature journal. Restoring a different burner waits for the pending turn. A confirmed run keeps its backend when Fund refreshes; changing RPC updates that backend's connection without discarding its build. Low funds leave the pending turn recoverable through Fund and the existing signature journal. A known program-check failure blocks new signatures, keeps the journal and continues the current run offline. Restoring a burner also continues the current run offline so later turns cannot silently use the previous key.

## Redeploy and publish

Run `RPC_URL=https://api.devnet.solana.com pnpm deploy:v1` with the creator key at `.tmp/keys/creator.json` funded on devnet. The deploy script selects devnet by genesis hash; a different genesis is accepted as localnet only on localhost. It verifies finalized templates, resumes incomplete uploads, preserves immutable occupied IDs and writes `play/deployments/<cluster>.json` after the lookup table is ready. Devnet manifests record the public default RPC; a private deployment endpoint stays out of the browser bundle. Then rebuild and run the chain corpus before publishing. `RPC_URL` also selects the matching manifest for `pnpm e2e:v1`.

`.github/workflows/pages.yml` installs with pnpm on Node 22, builds `play`, uploads `play/dist` and deploys Pages. The workflow follows the [GitHub Pages starter](https://github.com/actions/starter-workflows/blob/main/pages/static.yml). `.gitignore` explicitly includes the vendored SDK distribution needed by build checks. No repository was created. The code-navigation helper internally invoked read-only `git rev-parse` before failing; this crossed the no-git instruction. It changed no repository state, and the helper was not used again. A production build without `devnet.json` intentionally ships offline-only and explains that in Fund.

## Devnet deployment

Deployed on 2026-10-24 by creator `9aBiHCJpC2SyQLdqMrprF2N6HgcMPuCwunyasAYbSXzf`, template IDs 11000 to 11024, against Ballista programdata slot 507526156. The deploy took 101 upload transactions plus the lookup table and cost about 0.26 SOL. `play/deployments/devnet.json` is the result.

`RPC_URL=https://api.devnet.solana.com E2E_PLAYER=<funded keypair file> pnpm e2e:v1` played seed 4 to a win on devnet: 10 turns, 121 transactions, every state and event equal to the simulator. The burner spent 0.0039 SOL, of which 0.0033 is the one-time rent for its two entries. A turn took 25 to 32 seconds.

A browser run against the production build funded a fresh burner, started on chain and played three waves: 38 transactions, none failed.

Three fixes came out of these runs:

- The public endpoint answers bursts with HTTP 429. `RpcConnection` now sends a refused request again after 1, 2, 4, 8 and 15 seconds. A 429 means the node did not take the request, so this is safe for signed transactions too.
- Confirmation reads one signature status per poll and fetches the receipt only once the status is confirmed. Before, each poll made three requests.
- One start transaction never landed. Sends now leave RPC retries on, and while a signature has no status the client sends the same signed bytes again every fifth poll. One signature lands at most once, so this cannot apply a turn twice.

A turn's 12 transactions take about 25 seconds to confirm. "Next wave" and planning no longer wait for them; only Fight waits until the previous turn is confirmed.
